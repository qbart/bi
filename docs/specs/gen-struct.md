# `bi gen struct` — the schema as code

A `.bischema` says what a `Weapon` is; the game that loads `level1.bidata`
needs the same thing said in its own language. Typing it twice is how the
two drift. `bi gen struct` reads the schema and writes the types — structs,
enums, their defaults — in C, C++, Go, Rust, C3 or Lua, so the schema stays
the one source and the code is a build step away.

```
bi gen struct --lang <lang> -o <dir> -i <file>... [-m <file>...] [--pkg <name>] [--force]
```

## Status

**Proposed.**

## The command

```
--lang <lang>     c | c++ (cpp) | go | rust | c3 | lua — one per run
-o <dir>          where the files go; made, with its parents, when missing
-i <file>         a .bischema or .bidata; repeatable; a data file brings its schema
-m <file>         a .bimapping; repeatable; later files win on the keys they share
--pkg <name>      the namespace, package or module the types are declared in
--force           overwrite without asking
-v                say what was decided: the mapping merge, the notes, every file's fate
```

`-i` and `-o` are required. Flags may come in any order; a value starting
with `-` is refused as a missing value, `--` ends the flags. `--lang`
twice is an error: one language per run, the second run has the same
input line and a different `-o`. The alias `cpp` exists because `c++` is
not a bare key in TOML (see *The mapping file*) and a name that has to be
spelled two ways is better acknowledged than discovered.

### Inputs

Every `-i` is read before anything is generated, and a file that does not
parse stops the run with the format's own diagnostics — the ones the
property view shows — prefixed by the path. Nothing is written when
anything is wrong: generated code half-written beside code that compiled
yesterday is worse than no code.

A `.bidata` names its schema by `$schema`, and that schema is loaded as if
it had been given. Two inputs that lead to the same schema (a schema given
twice, or twice by data files) count once, by canonical path. A data file
that fails the format's validation against its schema (a `300` in a `u8`)
is an error like any other; a warning (a dangling ref, an unknown key) is
printed and does not stop the run.

The set of schemas is the set of *units*: each writes one file, named
after the schema's stem (`game.bischema` → `game.h`, `game.go`, …). Two
schemas with one stem in two directories collide on that name and are
refused; so are two schemas that define the same type name, because with
one `--pkg` they land in one namespace — run them into two directories, or
map one of the pair externally.

Data files contribute one more thing: **ids**. Every `($type, $id)` in the
data files given becomes a constant in the type's language, so
`weapon.drops` can be written `[WEAPON_RUSTY_SWORD]` rather than
`["rusty_sword"]` and the compiler catches the typo. Only the files on the
command line are scanned — not the project around them, because a command
line whose output changes with the directory's contents cannot be put in a
Makefile (`cli.md`). `ids = false` in the mapping turns the constants off.

### Output

Files are built in memory, then written, and the policy per file is:

| The path…                   | Does                                                       |
|-----------------------------|------------------------------------------------------------|
| does not exist              | is written                                                 |
| holds exactly this text     | is left alone, reported as `unchanged`                     |
| holds something else        | asks `overwrite game.rs? [y/N/a/q]` — `a` says yes to the rest, `q` stops |
| … and `--force` was given   | is written                                                 |
| … and stdin is not a terminal | is skipped and reported; the run exits non-zero, naming `--force` |

The unchanged case matters more than it looks: two schemas generated into
one directory both bring the support file (below) with identical text, and
a build that regenerates on every run must be silent when nothing moved.
A write goes to a sibling temp file and is renamed over the target, so an
interrupted run leaves the old file or the new one, never half of either.

Generated text is a pure function of the inputs: types in schema order (or
dependency order where the language demands it), imports sorted, no
timestamp, no bi version in the header. A regenerated file that did not
change is byte-identical, which is what lets it live in `git`.

Every file opens with a comment naming its origin:

```
// generated by `bi gen struct` from game.bischema — do not edit
```

## What is generated

For every struct and enum in the schema, its counterpart; for every
struct, its defaults; for every struct with instances in the data given,
its ids; and once per output directory, the support types the format's
builtins need.

### Types

| bi                 | C                          | C++                    | Go                | Rust              | C3                    | Lua (annotation)       |
|--------------------|----------------------------|------------------------|-------------------|-------------------|-----------------------|------------------------|
| `bool`             | `bool`                     | `bool`                 | `bool`            | `bool`            | `bool`                | `boolean`              |
| `i8` … `i64`       | `int8_t` … `int64_t`       | `std::int8_t` …        | `int8` … `int64`  | `i8` … `i64`      | `ichar short int long`| `integer`              |
| `u8` … `u64`       | `uint8_t` … `uint64_t`     | `std::uint8_t` …       | `uint8` … `uint64`| `u8` … `u64`      | `char ushort uint ulong` | `integer`           |
| `f32`, `f64`       | `float`, `double`          | `float`, `double`      | `float32`, `float64` | `f32`, `f64`   | `float`, `double`     | `number`               |
| `string`           | `const char *`             | `std::string`          | `string`          | `String`          | `String`              | `string`               |
| `rgb`, `rgba`      | `bi_rgb`, `bi_rgba`        | `bi::Rgb`, `bi::Rgba`  | `Rgb`, `Rgba`     | `Rgb`, `Rgba`     | `Rgb`, `Rgba`         | `Rgb`, `Rgba`          |
| `curve`            | `bi_curve`                 | `bi::Curve`            | `Curve`           | `Curve`           | `Curve`               | `Curve`                |
| `gradient`         | `bi_gradient`              | `bi::Gradient`         | `Gradient`        | `Gradient`        | `Gradient`            | `Gradient`             |
| enum `E`           | `enum E` + `E_VALUE`       | `enum class E`         | `type E string` + consts | `enum E`   | `enum E`              | `E = { value = "value" }` |
| struct `S`         | `struct S`                 | `struct S`             | `type S struct`   | `struct S`        | `struct S`            | `---@class S`          |
| `list<T>`          | `struct { T *items; size_t len; }` | `std::vector<T>` | `[]T`            | `Vec<T>`          | `T[]`                 | `T[]`                  |
| `optional<T>`      | `struct { bool set; T value; }` | `std::optional<T>` | `*T`             | `Option<T>`       | `T?`                  | `T?`                   |
| `ref<S>`           | `bi_ref` (`const char *`)  | `bi::Ref<S>`           | `Ref[S]`          | `Ref<S>`          | `Ref{S}`              | `string` (`# ref<S>`)  |

The support types — colours, curve, gradient, `Ref` — live in one file per
output directory, `bi_types.<ext>`, holding only the ones the schemas use
and the mapping did not replace; no file when that is nothing. `Ref<S>` is
a string with the target's type on it: the data stores ids, the loader
that turns ids into handles is not this command's, and a typed wrapper
means `Ref<Weapon>` cannot be handed to a field of `Ref<Enemy>` on the
way. C cannot type it and gets a comment naming `S` instead. A schema
called `bi_types.bischema` is refused, since its file would be the support
file's.

Enums are stored by name in the data, so the generated enum keeps the
names: a Go enum is a string type whose constants *are* the wire names, a
Rust or C or C3 enum comes with a `NAMES` table in value order, Lua's is a
table of the names. A loader written in any of them has what it needs.

Layout keys (`group`, `label`, `widget`, `show_if`…) are the editor's and
are not generated. `doc` becomes a doc comment on the type or field.
`min`/`max`/`step` go into the doc comment too — `damage: 0..999` — and
nowhere else in this version; a constant per bound is a mapping switch for
another day.

### Names

Each language gets its own idiom, and the schema's spellings are kept as
*wire names* wherever the language can hold them (a `serde` rename when
the Rust `derive` includes it, a `json:"…"` tag in Go, a comment in C), so
a loader knows what key a field came from.

| Language | Types    | Fields       | Enum values             | Id constants            |
|----------|----------|--------------|-------------------------|-------------------------|
| C        | as-is    | as-is        | `RARITY_COMMON`         | `WEAPON_RUSTY_SWORD`    |
| C++      | as-is    | as-is        | as-is                   | `Weapon::RUSTY_SWORD`   |
| Go       | Pascal   | Pascal       | `RarityCommon`          | `WeaponRustySword`      |
| Rust     | Pascal   | snake        | Pascal                  | `weapon::RUSTY_SWORD`   |
| C3       | as-is    | as-is        | `COMMON`                | `WEAPON_RUSTY_SWORD`    |
| Lua      | as-is    | as-is        | as-is                   | `Weapon.ids.rusty_sword`|

"As-is" is the bi identifier untouched — `[A-Za-z_][A-Za-z0-9_]*`, which
every one of the six accepts. Enum values are *strings*, not identifiers:
`"very rare"` and `"1st"` are legal in a schema and legal in no language,
so a value is made an identifier by turning every other character into
`_` and prefixing `_` to a leading digit, and the wire name is kept in the
`NAMES` table.

Three things can go wrong, and each is an error naming both sides and the
mapping key that fixes it:

- **A reserved word.** `type`, `default`, `class`, `func`, `end`, `then`,
  `union` — every language has a list, and each name is checked against
  the target's. Rust spells it `r#type`; the others get `type_`. Go's
  Pascal case sidesteps most, and `_` alone — a legal bi identifier, Go's
  blank identifier — does not. A name that is still reserved after the
  suffix (C's `_Foo` and `__foo` are the implementation's) is refused.
- **A collision after casing.** `foo_bar` and `fooBar` both become
  `FooBar` in Go; `"rare"` and `"Rare"` both become `Rare` in Rust;
  `"very rare"` and `"very-rare"` both become `very_rare` everywhere. Two
  names that map to one are refused rather than numbered.
- **A name the language owns.** A struct called `String` in Rust, `Rgb`
  beside the support type, `Weapon` twice across two schemas.

The fix is always the same: `[names]` in the mapping says what the name is
in the code.

### Defaults

The schema's defaults are what make sparse data loadable, so they travel
with the types. Each language gets them in its own shape:

| Language | Shape                                                                 |
|----------|-----------------------------------------------------------------------|
| C        | `void weapon_init(struct Weapon *)`; list and curve defaults as `static const` arrays it points into |
| C++      | default member initialisers — `int32_t damage = 10;`                  |
| Go       | `func DefaultWeapon() Weapon`                                          |
| Rust     | `impl Default for Weapon`                                              |
| C3       | `fn Weapon Weapon.default()`, since C3 has no member initialisers on structs |
| Lua      | `Weapon.new(t)` — copies `t`, fills what it lacks from the defaults   |

Values are the schema's, fully resolved: a struct-typed field's partial
default is completed from the struct's own defaults (`Schema::resolve`),
an enum's is its first value, a `ref`'s absent default is the empty id —
the same unset marker `:bi new` writes. Number literals are spelled for
the type (`1.0f` for a C++ `float`, `1.0` for an `f64`); strings are
escaped for the language, including `"` `\` and every control character,
and non-ASCII is passed through as UTF-8, which all six read.

An externally mapped type has no default the generator can spell. The
field then gets the language's own default of that type — Rust
`Default::default()`, C++ `{}`, Go and C3 and C the zero value, Lua `nil`
— and the run prints one note per such field so nobody wonders why
`offset.x` stopped being `0.5`. A mapping can say what to write instead:
`default = "Vec2::ZERO"` on the type's entry.

### Order and recursion

The schema allows recursion through `list`, `optional` and `ref`, and C,
C++ and C3 want a type complete before it is embedded. Structs are
therefore emitted in dependency order — an embedded or optional field's
type before the struct that holds it — with every struct forward-declared
first, ties broken by schema order; Go, Rust and Lua keep schema order,
which reads better and which they do not care about.

A cycle through `optional` is legal in the format and unsized in two of
the languages: `Enemy { leader: optional<Enemy> }` is `Option<Enemy>`
inside `Enemy`, which Rust refuses, and `std::optional<Enemy>` inside
`Enemy`, which C++ refuses. The generator boxes the edge that closes the
cycle: `Option<Box<Enemy>>`, `std::unique_ptr<Enemy>`, C's `Enemy *`. A
`list` in a cycle is fine everywhere — a vector of an incomplete type is a
pointer under the hood — and so is a `ref`, which is a string.

### Namespaces — `--pkg`

`--pkg a.b` is one dotted path for every language, and each takes what it
can hold:

| Language | `--pkg gen.scriptableobjects` becomes                                   |
|----------|-------------------------------------------------------------------------|
| C++      | `namespace gen::scriptableobjects { … }`                                |
| Go       | `package scriptableobjects` — the last segment; Go's package is its directory, and `-o` is that directory |
| C3       | `module gen::scriptableobjects;`                                        |
| Lua      | the `require` prefix: `require("gen.scriptableobjects.bi_types")`       |
| Rust     | nothing — a Rust module is its file; the note says `mod game;` and `mod bi_types;` go where the files went |
| C        | nothing — the note says so, and `prefix` in the mapping is the C way    |

`-o` and `--pkg` are independent on purpose: the directory is where the
build expects the files, the package is what the build expects inside
them, and a generator that derived one from the other would be right for
one build layout and wrong for the rest. Without `--pkg`, C++ emits no
namespace, Go emits `package <dir name>` — the one thing Go will not do
without — C3 emits `module <stem>;`, Lua requires by bare name.

A segment that is not an identifier in the target language is refused.

### Lua

A Lua "struct" is a table, and what a generator can add is the part the
language leaves out: shape and defaults. Each type is an
[LuaLS](https://luals.github.io/) annotated class — `---@class Weapon`,
`---@field damage integer  # 0..999` — with `Weapon.new(t)` filling
defaults, each enum a table of its names, each set of ids a table under
the type. The module returns a table of the types. Integers beyond 2⁵³ in
a `u64` field are Lua 5.3+ integers and lose nothing; on 5.1/LuaJIT they
are doubles, which the doc comment says.

## The mapping file — `.bimapping`

A `.bimapping` is TOML. The alternatives were weighed: YAML would be a new
dependency with its own traps (a `no` that reads as `false`, a version
number that reads as a float), and JSON cannot hold a comment, which a
file a human writes and reads back a year later needs. TOML is already
here for `.bi.toml` and `config.toml`, and `toml_edit` keeps spans, so an
error is `weapons.bimapping:12: unknown key `derives`` and not "something
in the mapping".

It answers two questions: *what is not generated because the project
already has it* — the `Vec2` the engine ships, the `Color` the renderer
wants — and *how the generated code is spelled*. Neither changes what the
data means; the mapping never touches the wire format.

```toml
# weapons.bimapping — control for `bi gen struct`; every key optional.

ids = true                       # id constants from the data files given

[names]                          # what a schema name is called in code, every language
"Weapon.type" = "kind"           # a field
"Rarity.very rare" = "VeryRare"  # an enum value
"Enemy" = "Monster"              # a type; the wire name stays "Enemy"

[rust]
imports = ["use serde::Deserialize;"]
derive  = ["Debug", "Clone", "Deserialize"]   # `Deserialize` turns on serde renames
header  = "#![allow(dead_code)]"              # text after the generated-by line

[rust.types]
Vec2 = "glam::Vec2"                           # external: not generated, spelled so
rgb  = { as = "palette::Srgb<u8>", import = "use palette::Srgb;", default = "Srgb::new(0, 0, 0)" }

[rust.generics]
list     = "SmallVec<[{T}; 4]>"               # {T} is the element's spelling
optional = "Option<{T}>"
ref      = "Handle<{S}>"                      # {S} is the target struct's spelling

[rust.names]                                  # like [names], for one language
"Weapon.name" = "display_name"

[cpp]                                         # c++ on the command line, cpp here
imports = ["#include <glm/vec2.hpp>"]
[cpp.types]
Vec2 = "glm::vec2"

[c]
prefix = "gs_"                                # every type and constant: gs_Weapon, GS_RARITY_COMMON
[c.types]
Vec2 = { as = "vec2", import = "#include \"math/vec2.h\"" }

[go]
imports = ["github.com/go-gl/mathgl/mgl32"]
[go.types]
Vec2 = "mgl32.Vec2"
```

Per language, the keys are:

| Key         | Meaning                                                              |
|-------------|----------------------------------------------------------------------|
| `imports`   | Lines placed once at the top of every unit — `use`, `#include`, Go import paths |
| `types`     | Schema type or builtin name → the spelling to use instead of generating it; the long form adds an `import` for it and a `default` |
| `generics`  | `list`, `optional`, `ref` → a template with `{T}` (or `{S}` for `ref`) |
| `names`     | `[names]` for this language only; wins over the shared one           |
| `header`    | Text after the generated-by comment, before the imports              |
| `prefix`    | C: prepended to every type and constant                              |
| `derive`    | Rust: the derive list on every type; `Deserialize`/`Serialize` add `#[serde(rename = "wire")]` where the code name differs |

A mapping key that names a type no schema in the run has is a warning,
not an error: one mapping is meant to serve every schema in a project,
and a project rarely uses every type everywhere. A key that is not one of
the above is an error with its line. Several `-m` files merge in order,
the later winning per key, and the merge is printed under `-v`; two files
disagreeing about `Vec2` is a thing to see, not to guess.

Mapping a builtin (`rgb`, `curve`) externally removes it from
`bi_types.*`; mapping every builtin every schema uses removes the file.
Mapping a schema struct externally removes its definition, its default
and its ids; a struct that embeds it still carries a field of the
external spelling, and a struct that `ref`s it still gets `Ref<Vec2>`
with the external spelling inside the angle brackets, which is the
project's problem to make sense of and the note says so.

## Edge cases

Collected here, each with what the generator does.

| Case                                                           | Does                                                                  |
|----------------------------------------------------------------|-----------------------------------------------------------------------|
| No `types` in a schema                                         | Writes the unit with only its header; a note says the schema is empty |
| A struct with no fields                                        | C and C3 refuse an empty struct: a `char bi_empty_;` pad member, commented; the rest emit it empty |
| An enum value that is not an identifier (`"very rare"`, `"1st"`, `""`) | Made one as under *Names*; the empty string becomes `_empty`; the wire name kept in `NAMES` |
| A name reserved in the target                                  | Suffixed (`r#` in Rust), or refused when still reserved               |
| Two names that case to one                                     | Refused, naming both and the `[names]` key                            |
| `optional<S>` on a cycle                                       | Boxed on the closing edge                                             |
| `optional<list<T>>` in Go                                      | `*[]T`: the pointer says null, the slice says empty — the format tells them apart and so must the code |
| `optional<ref<S>>` in C                                        | `struct { bool set; bi_ref value; }` like any optional                |
| `u64` in Lua                                                   | `integer`; the doc comment notes the 5.1 double                        |
| `i64` default above 2⁵³ in Go/Rust/C literals                  | Exact — the JSON number is an integer and is printed as one            |
| A float default with no fraction (`1`) on an `f32`             | Spelled `1.0` / `1.0f` so C++ and Rust type it as a float              |
| `-0.0`, `NaN`, `inf`                                           | `-0.0` kept; the other two cannot be in JSON and cannot arrive         |
| A string default with `"`, `\`, a newline, an emoji            | Escaped per language; UTF-8 passed through                             |
| A `curve` default                                              | The support type's literal: an array of `[x, y, in, out]` points, in C a `static const` array pointed into |
| A `gradient` default with a six-digit colour                   | Read as opaque, written eight-digit — the format's own rule           |
| A `ref` with no default                                        | The empty id, and a doc comment saying it is required                  |
| An externally mapped type with a schema default                | The language's default, a note, or the mapping's `default`             |
| A mapped `list` template without `{T}`                         | Refused: `rust.generics.list must contain {T}`                        |
| `--pkg` for C or Rust                                          | Accepted, one note, no effect                                          |
| `--pkg` with a segment that is not an identifier (`gen.2d`)    | Refused                                                                |
| Go with no `--pkg` and `-o .`                                  | `package <name of the current directory>`; refused when that is not an identifier |
| Two schemas, one stem                                          | Refused, naming both paths                                             |
| Two schemas, one type name                                     | Refused, naming both                                                   |
| A schema named `bi_types`                                      | Refused                                                                |
| A data file whose `$schema` is missing                         | The format's error, with the data file's path                          |
| The same schema through two data files                         | One unit; the ids of both files                                        |
| Two data files, one `($type, $id)`                             | The format's duplicate-id error                                        |
| An id that cases onto another (`rusty_sword`, `RustySword`)    | Refused like a field collision                                         |
| `-o` names a file                                              | Refused                                                                |
| `-o` cannot be made (permissions, a file in the way)           | Refused before anything is generated                                   |
| A target that exists and is unchanged                          | Left alone, `unchanged`                                                |
| `q` at the overwrite prompt                                    | Stops; files already written stay, the rest are listed                 |
| No terminal, no `--force`, a differing target                  | Skipped, listed, non-zero exit                                         |
| Interrupted mid-write                                          | The rename is atomic: old file or new file                             |
| Two `-m` files that both map `Vec2`                            | The later wins; `-v` shows the merge                                   |
| A mapping for a language other than `--lang`                   | Ignored — one file serves every language                               |
| A mapping naming a type no schema has                          | Warning                                                                |
| Layout keys, `show_if`, `widget`                               | Not generated; they are the editor's                                   |
| A `.bidata` given with `ids = false`                           | Contributes its schema and nothing else                                |

## Where it lives

The command is a library function with a thin frontend, so a GUI, an
editor command (`:bi gen struct` later) or a build tool can call the same
thing without a process.

```
src/gen/mod.rs           pub mod structs — the generators grow here; `sample` may move in
src/gen/structs/mod.rs   generate(&Request) -> Result<Output, Vec<Diagnostic>>
src/gen/structs/model.rs the language-neutral model: units, types, resolved
                         defaults, ids, dependency order, boxed edges
src/gen/structs/mapping.rs  Mapping::parse, merge — TOML in, spans on every error
src/gen/structs/names.rs cases, reserved words per language, collision checks
src/gen/structs/lang/{c,cpp,go,rust,c3,lua}.rs   one Backend each
src/gen/structs/write.rs the file policy, with the question asked through a trait
```

```rust
pub struct Request {
    pub lang: Lang,
    pub pkg: Option<String>,
    pub inputs: Vec<(PathBuf, String)>,    // path and text; the caller reads files
    pub mappings: Vec<(PathBuf, String)>,
}
pub struct Output {
    pub files: Vec<OutFile>,               // relative paths, text
    pub notes: Vec<Diagnostic>,            // warnings and notes, never errors
}
pub struct OutFile { pub path: PathBuf, pub text: String }

pub trait Backend {
    fn lang(&self) -> Lang;
    fn unit(&self, unit: &Unit, model: &Model, mapping: &LangMapping) -> Result<String, Vec<Diagnostic>>;
    fn support(&self, model: &Model, mapping: &LangMapping) -> Option<String>;
}

pub enum Overwrite { Yes, No, All, Quit }
pub trait Ask { fn overwrite(&mut self, path: &Path) -> Overwrite; }
pub fn write(dir: &Path, files: &[OutFile], force: bool, ask: &mut dyn Ask) -> Result<Report>;
```

The library takes text, not paths, for the same reason `Schema::parse`
does: a test hands it strings, an editor hands it buffers, and only
`main.rs` touches the disk. It never prompts: the terminal frontend's
`Ask` reads a line, a GUI's opens a dialog, a test's answers from a
script, and the `--force`/not-a-tty cases are two more `Ask`s that always
say `All` or `No`. The model is built once and every backend reads the
same one, so a name collision or a boxed cycle is found in one place and
found the same way for all six.

`Schema::parse`, `data::parse`, `Schema::resolve` and `TypeExpr` are
reused as they are. `main.rs` gains `Invocation::GenStruct` carrying the parsed flags, the
flag parser for it, and the `Ask` that talks to the terminal.

Out of scope, and shaped for: loaders. `bi gen load` would write the
`.bidata` reader in each language — two passes, ids into handles — and
everything it needs is already kept here: wire names on every field and
value, the `NAMES` tables, the typed `Ref`.

## Tests

In `gen/structs`:

- **model**: dependency order puts `Vec2` before `Weapon`; a cycle through
  `optional` marks its closing edge boxed and a cycle through `list` does
  not; a partial struct default resolves through the struct's own; ids
  are collected per type across two data files; two schemas with one type
  name are refused.
- **names**: `foo_bar` and `fooBar` collide in Go and not in C; `type`
  becomes `r#type` in Rust and `type_` in C; `"very rare"` and `"1st"`
  become identifiers; `_` is refused in Go; `[names]` overrides win.
- **mapping**: every key in the example above parses; an unknown key is
  refused with its line; two files merge with the later winning; a `list`
  template without `{T}` is refused; a type no schema has is a warning.
- **each backend**, against the sample schema: the full expected text —
  types, defaults, enum names, ids, the support file, `--pkg` in its
  place; every generic composition (`list<ref<Weapon>>`,
  `optional<list<i32>>`, `list<list<f32>>`); an external `Vec2` leaves
  the definition out and the spelling in; a boxed cycle.
- **write**: fresh, unchanged, differing with each answer, `--force`, the
  non-tty refusal, the atomic rename; every case through a scripted `Ask`.

In `tests/`: the Rust output for the sample schema is generated by a test
and compiled — `include!`d into the test crate — which is the one language
whose toolchain the test suite already has. `scripts/gen_struct_compile.sh`
generates all six from `examples/props` and compiles each with whatever
compiler is on the path, skipping the ones that are not; it is run by
hand like `vim_differential.py`, not by `cargo test`.

In `main.rs`: `bi gen struct` without `-i` or `-o` says which; `--lang`
twice, an unknown language, a value that starts with `-`, are refused
naming the flag; `bi gen` lists `struct` beside `sample`.
